## Decisions
- Do not use late V LDS reload. It failed correctness because V LDS storage is reused/overwritten by later Q/DO/D/DS stages; `v_reg_tensor` must be captured before that reuse.
- Do not use repeated partial global DQ update for one DQ tile. It was numerically plausible but too slow due repeated global update/atomic behavior.
- Probe/debug code is not reliable negative evidence when it perturbs register allocation or code shape. Treat bad results from invasive probes as “failed to solve” rather than proof of the underlying hypothesis.
- BF16 precision judgment uses two layers:
  - `max_abs_err / grad_scale`
  - `max_abs_err / max(abs(ref_grad))` or equivalent relative-to-reference metric
- Old static `BAD` flags alone are not authoritative for BF16. Causal BF16 BWD can show larger scale-normalized error if relative-to-reference stays comparable to PyTorch BF16 behavior.
- Do not compare absolute times across different scripts. Use the same benchmark script/settings for A/B.
- Do not use `HIP_LAUNCH_BLOCKING=1` for performance timing when stream overlap matters; use it only for correctness/path checks.
- `_hip` files are generated in principle, but this repo's build consumes `_hip.hpp`; edit both non-hip and hip mirrors during experiments.
- Avoid globalizing a D256-only win. For final merge, use problem-aware gating or D-specific branches when the data is shape-specific.

## UniDec Architecture Notes

This directory is a compact c18 FlashAttention/CK baseline copied for UniDec-side development. It is not the full original research workspace: large generated build artifacts, rocprof outputs, test outputs, and ISA dumps were intentionally left out. The goal is to keep enough source and runtime material to understand, rebuild, import, and reuse the ROCm CK FlashAttention path.

### What Is Included

- `csrc/`: low-level C++/HIP source tree. This is the main kernel source area.
- `csrc/composable_kernel/`: ROCm Composable Kernel subtree and CK Tile FMHA templates/codegen.
- `csrc/composable_kernel/include/ck_tile/`: core CK Tile tensor/window/GEMM/pipeline infrastructure.
- `csrc/composable_kernel/example/ck_tile/01_fmha/`: CK Tile FlashAttention integration, FMHA host wrappers, traits, runners, and generated-kernel source templates.
- `csrc/composable_kernel/example/ck_tile/01_fmha/codegen/`: Python codegen for FWD/BWD/paged-kv/split-kv kernels. This is where many kernel instances are selected and emitted.
- `csrc/flash_attn_ck/`: flash-attn CK binding/wrapper layer, including normal FWD/BWD, varlen, and `fwd_kvcache`/paged KV entry points.
- `flash_attn/`: Python package wrapper. This is needed to call the compiled extension from Python.
- `setup.py`: build orchestration. It invokes CK codegen, chooses source lists, forwards CK debug/optimization macros, runs hipify/rename steps, and builds `flash_attn_2_cuda`.
- `flash_attn_2_cuda.cpython-312-x86_64-linux-gnu.so`: copied c18 compiled extension for the current Python 3.12 + ROCm/gfx1100 environment.
- `test_ck_tile_probe.py`, `benchmark_torch_vs_flash_attn_plot.py`, `scripts/`: minimal validation, benchmark, profiling, and prebuilt-install helpers.

### Source Of Truth

Do not treat `build/*.hip` as source of truth. Those files are generated by `setup.py` and CK codegen. In this compact copy, `build/` was not copied because it is disposable and can be regenerated.

For CK backend kernel logic, prefer editing or studying:

- `csrc/composable_kernel/include/ck_tile/...`
- `csrc/composable_kernel/example/ck_tile/01_fmha/*.hpp`
- `csrc/composable_kernel/example/ck_tile/01_fmha/codegen/...`
- `csrc/flash_attn_ck/*.cpp`

The `_hip.hpp` files are hipified/generated mirrors in this codebase. When both non-`_hip` and `_hip` versions exist, use the non-`_hip` version as the reference unless the build path proves otherwise.

### Build/Data Flow

The effective build chain is:

1. Python API calls live under `flash_attn/`.
2. PyBind extension entry points are provided by `csrc/flash_attn_ck/flash_api.cpp`.
3. `setup.py` collects wrapper sources and generated CK kernel instance sources.
4. CK codegen emits many `fmha_*` kernel translation units into `build/`.
5. `hipcc` compiles those generated HIP/CU files plus wrapper sources.
6. The final extension is linked as `flash_attn_2_cuda.cpython-312-x86_64-linux-gnu.so`.

Therefore, `csrc` is the low-level kernel source tree, but it is not sufficient alone for a usable package. For rebuild/import/test, keep `setup.py`, `flash_attn/`, and the validation scripts together with `csrc`.

### Existing Paged KV / Decode-Relevant Pieces

This baseline already contains paged/kvcache-related code:

- `csrc/flash_attn_ck/mha_fwd_kvcache.cpp` exposes `mha_fwd_kvcache` and accepts `block_table`, `page_block_size`, `cache_batch_idx`, optional new K/V, rotary, alibi, and sliding-window parameters.
- `csrc/composable_kernel/example/ck_tile/01_fmha/fmha_fwd.hpp` defines `fmha_fwd_pagedkv_args` and `fmha_fwd_splitkv_args`.
- `csrc/composable_kernel/example/ck_tile/01_fmha/codegen/ops/fmha_pagedkv_prefill.py` contains CK Tile paged-KV FWD codegen.

These are useful references for vLLM-style paged decode attention, but they should not be assumed to match vLLM's ABI or scheduler contract. vLLM decode usually has stricter runtime conventions around block tables, KV cache layout, context lengths, GQA/MQA grouping, quantized KV, block size, and scheduler-owned metadata.

Recommended development approach for UniDec/vLLM-style decode:

- Use this directory as the reference and source library.
- Start a separate isolated prototype/custom-op path for the new decode ABI.
- Reuse CK Tile primitives, memory-window code, paged-kv argument handling, and profiling scripts from this baseline.
- Only merge back into the flash-attn CK tree after the new decode path has a clean ABI contract, correctness tests, and per-kernel profiling evidence.

### Current c18 Performance/Correctness Context

The c18 baseline is a stable checkpoint, not a final fastest possible implementation. Its important status:

- FWD for D64/D128/D256 is strong on gfx1100.
- D256 BF16 BWD remains structurally slower than PyTorch best backend, mainly due to split backward kernels.
- The known D256 BF16 S2048 noncausal breakdown around c18 was dominated by `split_dk`, `split_dq`, and `split_dv`; `convert_dq` was negligible.
- BF16 correctness should be judged with two metrics:
  - `max_abs_err / grad_scale`
  - `max_abs_err / max(abs(ref_grad))`
- Old static absolute-error checks can falsely mark BF16 causal as BAD; use the dual metric standard unless investigating a clear outlier.

### Practical Rules For Future Work

- Keep experimental kernel paths isolated behind narrow macros or separate source files.
- Do not broadly apply no-edge or exact-tile assumptions without runtime dispatch guards.
- Do not edit generated `build/*.hip` files as durable source.
- For paged decode work, define the runtime ABI first, then design the kernel. Do not force-fit vLLM semantics into the current flash-attn `fwd_kvcache` wrapper unless the layouts and scheduler assumptions match exactly.
- For any CK Tile distribution/window change, verify the distributed tensor contract before trusting performance numbers.
